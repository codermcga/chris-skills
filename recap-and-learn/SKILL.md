# Summary and Tips

每轮面向用户的最终回复，先完成正常回答，再在末尾依次追加 Summary 和 Tips；不必等到整个项目结束。这两部分是额外的辅助内容，不得替代、压缩或削弱正常回答。仅影响当前回复的表达，不授予修改文件、记忆或其他 Skill 的权限。

正常回答应保持未启用本规则时应有的内容完整性和回答深度：根据用户的问题提供必要的解释、分析、方案、代码、操作步骤或工作结果。简单问题可以简洁回答，复杂问题按需展开；不必添加名为“正文”的标题或套用固定模板。

先形成完整的正常回答，再提炼 Summary、补充 Tips。检验标准是：即使删除 Summary 和 Tips，剩下的正常回答仍能完整、直接、有用地回应用户的原始请求。允许 Summary 与正文的核心结论适度重叠，不为了去重而省略正文或把正文降为摘要的补充。

## Summary

Summary 面向只读结论的用户。默认写 2～3 个无序列表要点，简单问题写 1 点即可；每点通常 1～2 句话，总体约 120～220 个中文字。长度只是参考：不为凑字数补充细节，也不为压缩删掉影响判断的条件。

不要使用“结果”“验证与边界”“影响”“后续”这类固定分类标签，也不要按这四类逐条展开。把同一件事的结论、限制和影响合并表达，避免同一事实在不同要点中重复。

用户只看 Summary，应当能知道本轮结论、当前完成程度、主要阻塞，以及是否需要自己采取行动。关键证据和未验证范围只在影响判断时简短融入结论；搜索目录、工具调用和完整操作过程留在正常回答中。

持续多轮的任务只保留理解当前状态所需的背景，不重复整段历史。区分“未找到”和“不存在”、“局部通过”和“全部通过”，不要把检查范围不足写成结论不成立。

## Tips

Tips 帮助用户理解本轮涉及的原理，并积累以后能复用的知识。默认写 1 个知识点；确实有两个独立且有价值的点时写 2 个，不为凑数量补充无关内容。

始终使用无序列表（`- `），不使用数字序号。每点用简短主题开头，再用 2～3 句话说明原理、原因或判断方法，必要时结合本轮任务举例。主题可以加粗。

优先讲以后工作也用得上的知识：本轮新出现且影响理解的概念、背后的机制、容易踩的坑，或判断同类问题的方法。首次介绍概念时给出中文名称、必要的英文全称和缩写，再用通俗语言说明它是什么、解决什么问题。

不要重复 Summary 的结论和进展，不把任务安排、进度或 Skill 本身的禁令当作知识点。已经解释过的概念不重复定义，可以补充它的用途、限制或与其他概念的联系；概念直接影响当前判断时，先在正常回答里说明，Tips 只做补充。

## 格式与兼容

标题固定使用英文 Summary 和 Tips，内容使用用户当前使用的语言。默认采用基础 Markdown：标题分别独占一行，写成 `**Summary**` 和 `**Tips**`，标题前后留空行，不加冒号。

Summary 和 Tips 均使用 `- ` 开头的无序列表。列表前留空行；每个条目另起一行，条目之间留空行。Summary 的要点直接陈述结论，不加分类标签；Tips 的要点可以用加粗的简短主题开头，例如 `- **缓存命中价**：解释。`。加粗标记内只放主题文字，不留首尾空格，冒号等分隔标点放在结束标记之外，避免 `**主题：**内容` 或 `**主题： **内容` 这类容易原样显示星号的写法。

这两部分不依赖表格、HTML、颜色、折叠块或平台专用指令。输出实际 Markdown 和换行，不转义成可见符号，也不用代码块包住整份回复。若已知目标客户端不支持 Markdown，或用户反馈这些基础写法仍不能正确显示，则改用独占一行的纯文本标题 Summary、Tips，以及普通文本列表和主题，保留分点结构，不显示加粗标记。无法确认客户端能力时使用上述基础 Markdown，不声称已验证所有 Agent 的显示效果。

## 例外与边界

用户要求只输出命令、代码、JSON、译文或其他严格格式，或明确要求省略这两部分时，遵循当轮要求；不得把 Summary 和 Tips 写进待复制的代码、文件、提交信息或其他交付物。已有其他 Skill 要求摘要或知识点时合并为一份，不重复添加。

提炼知识是帮助用户学习，不代表 Agent 已获得永久记忆。只使用可见上下文和已取得的证据，不假称记得不可访问的历史。信息不确定时说明适用条件或不确定性。
